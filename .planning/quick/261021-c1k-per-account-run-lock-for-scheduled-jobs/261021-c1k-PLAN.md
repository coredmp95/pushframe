<objective>
Serialize every write run against one Aura account with a per-account, kernel-held run lock (`fcntl.flock`), taken at CLI dispatch for the WHOLE run (session + listing + plan + apply) of every writing verb, so two scheduled jobs firing in the same `OnCalendar=daily` + `RandomizedDelaySec=15m` window can no longer double the write rate against the Pushd anti-abuse surface or race the persisted WriteBudget file (`WriteBudget.save()` does load, consume, `os.replace`, and the last writer wins).

Purpose: unattended multi-job operation without lost budget updates or doubled write bursts. A waiting job says who it is waiting for. A pathological wait ends as a named error with a remedy, never a traceback.

Output: new `pushframe/runlock.py`, one new setting, CLI dispatch wiring for sync/push/google-sync/reconcile, two new test files, docs (ERRORS.md, CLI.md, `config set --help`), and a CHANGELOG `[Unreleased]` entry. No release, tag or version bump.

User-agreed design (from the task description; there is no CONTEXT.md, so these IDs are labels for traceability):
- U-01: `fcntl.flock` on a per-account lock file under `~/.local/state/pushframe/`, keyed like the WriteBudget account key (`sha1(email)[:12]`).
- U-02: Held for the WHOLE run of google-sync, sync, push and reconcile-with-removal, never just the apply phase. The kernel releases it when the process dies: no stale-lock cleanup.
- U-03: Blocking wait; N waiters are fine (not FIFO, acceptable). The holder writes job/report-tag, pid and start time into the lock file. Waiters log it periodically (every few minutes).
- U-04: No short timeout. A configurable safety cap (default 12h) as a `PUSHFRAME_*` setting resolved at call time via `pushframe/utils/settings.py`. Hitting the cap raises a named typed error with a remedy, documented in docs/ERRORS.md.
- U-05: Dry-run and read-only paths (status, inspect, doctor, google-sync/sync without --apply) must NOT take the lock. Use the simplest correct option and justify it (see below).
- U-06: Offline-testable: lock dir, clock and poll interval are injectable. Real contention is tested with two processes. The offline suite stays green with DeprecationWarnings as errors.
- U-07: Build on 566a28f (`classify_write_failure`) and 90bfb15 (AWS credential refresh) without regressing them. Commit lines end with the Co-Authored-By trailer. No release/tag/publish. Add a CHANGELOG `[Unreleased]` entry.

Discretion choices (documented here so the executor does not re-decide them):
- Where the lock is taken: in `_main` dispatch, not inside `run_sync`/`run_google_sync`. This is one choke point that covers the session, listing, plan and apply; the `google-sync --all` loop takes it exactly once; and an in-process re-acquire can never self-deadlock (`flock` conflicts between two open file descriptions of the same process).
- Read-only gating (U-05): no lock at all, decided from the parsed write flag (`--apply` for sync/push/google-sync, `--remove` for reconcile) before any network call. Rejected alternative 1: a shared `LOCK_SH` for readers. A dry-run would then sit behind an hours-long nightly apply, and readers mutate neither the frame nor the budget file. Rejected alternative 2: lock only around apply. The user explicitly rejected that because of stale plans. `doctor` stays lock-free per U-05 (it is a deliberate one-probe diagnostic).
- How the wait works: poll `flock(LOCK_EX | LOCK_NB)` every `poll_interval` (default 5 s) instead of a bare blocking `flock`. A blocking call cannot honor a cap or log periodically without threads or signals. The poll keeps the same semantics (the kernel arbitrates, the lock is released on death, waiters are not FIFO) at no more than 5 s extra latency on an hours-long wait, and it is fully injectable (`sleep`, `monotonic`, `now`, `out`).
- No account identity (no env email, no stored session): skip the lock and print a named stderr note. This mirrors `_build_write_budget`'s existing "pacing skipped" contract. Scheduled jobs always carry a stored session, so they are always locked.
- Lock file: `~/.local/state/pushframe/locks/account-<account_key>.lock`, resolved at call time. The directory is 0700 and the file 0600. The file is never unlinked, because unlinking a live lock file breaks mutual exclusion. The holder info contains no email, token, album, link or path: only pid, job tag, verb and start time.

Mechanics:
- `ensure_private_dir(dir)`.
- Open with `os.open(path, os.O_RDWR | os.O_CREAT | os.O_NOFOLLOW | os.O_CLOEXEC, 0o600)` plus `os.fchmod(fd, 0o600)`. NEVER pass O_TRUNC: it would wipe a live holder's info.
- Wrap any OSError from mkdir/open as AccountLockError: 'cannot open the account lock file <path> (<strerror>) — fix the permissions of <dir>; nothing was changed'.
- Loop: try `fcntl.flock(fd, LOCK_EX | LOCK_NB)`. On success, break. Catch ONLY BlockingIOError as contention; any other OSError from flock becomes AccountLockError. Then compute elapsed from the injected monotonic. If elapsed has reached the next log time, emit a waiting line and advance the next log time by log_every (the first line is due at 0). If elapsed is at least max_wait, raise AccountLockTimeout. Otherwise sleep min(poll_interval, max_wait - elapsed).
- On success after any wait, emit 'account lock acquired after <dur> — starting'.
- Then write the holder JSON {pid: os.getpid(), job, command, started_at: now().isoformat(timespec='seconds')} with `os.ftruncate(fd, 0)` plus `os.pwrite(fd, data, 0)`.
- The waiter reads holder info with `os.pread` on its own fd (tolerant: empty, partial or bad JSON gives None).

Message formats (tests assert these substrings):
- Waiting line: 'waiting for account lock held by <who> since <since> — waited <dur> of max <cap> (PUSHFRAME_ACCOUNT_LOCK_MAX_WAIT); this run starts when that one ends'.
