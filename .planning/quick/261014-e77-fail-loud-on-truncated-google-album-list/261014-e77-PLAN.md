<objective>
Fail loud on a truncated Google album listing that is currently accepted as complete.

PROD INCIDENT (venus, 2026-10-13 22:08 UTC, pushframe 5.1.32, scheduled `google-sync 'Cadre' --frame 'Cadre de Fabrice' --apply --yes --scheduled`): album "Cadre" metadata item_count = 757; the first snAcKc page returned 300 items with NO AH_ continuation token, `enumerate_album` stopped (`next_token is None` -> exhausted_cleanly=True), the plan read "300 unchanged, 457 to hide" and `Videos skipped: 457` silently relabelled the truncation as videos. Only the SAFE-02 20% mass-hide gate in --scheduled mode saved 457 photos; a manual `--apply --yes` would have hidden them. A read-only re-run minutes later returned 300+300+157 = 757 with tokens — the missing token is a transient Google answer.

Requirement IDs (from the quick-task description's "Required fix"):
- E77-1 — enumerator: `expected_count` opt-in + one bounded same-cursor retry on a tokenless full page; a persisting tokenless full page beyond tolerance returns exhausted_cleanly=False so the existing truncated_listing gate fires.

- E77-3 — other callers + report: check every enumerate_album caller; verify (and pin with a test) that the scheduled ERROR email names the real cause.

Purpose: an untrusted, transiently-truncated upstream answer must never drive a destructive plan (mass hide) nor be misreported to the operator.
Output: hardened `pushframe/google/enumerate.py` + `pushframe/gsync.py`, offline TDD tests reproducing the incident shapes, full offline suite green. No version bump, no release.
